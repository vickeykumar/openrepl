# LLD 15: Object storage (backups and workspace snapshots)

Status: implemented (2026-11-01). Scope: `src/objstore` (the S3 client), `src/backup` (backups and restore of this server's own files), `src/homesnap` (snapshots of signed-in users' workspaces), `src/utils/{config,jobregistry}.go`, `src/server/{settings_keys,admin_health,identity,gateway}.go`, `src/gotty/main.go`.

## 1. Why

A host that keeps no disk between deploys (Render's free tier) loses `/opt/gotty` (the database files, the settings, the audit log, the usage totals) and the workspaces of signed-in users. MongoDB or Firestore already keep the databases for a server that uses them; the audit log, the totals and every workspace are only on disk. An object store (S3 API: Cloudflare R2, AWS S3, MinIO, RustFS) holds a copy and gives it back. It is not a primary store: a database that updates keys all the time does not fit it.

## 2. Settings

| Setting | Meaning |
|---|---|
| `OPENREPL_S3_ENDPOINT`, `_BUCKET`, `_ACCESS_KEY_ID`, `_SECRET_ACCESS_KEY` | All four are needed (`utils.S3Enabled`). The key id and the secret can also be saved in the dashboard (Site settings, API keys), encrypted like the other keys (`settings_keys.go`; a pair is checked with the bucket when the second one is saved). |
| `OPENREPL_S3_REGION` | `auto` (R2's) when not set. |
| `OPENREPL_S3_PREFIX` | Put before every key. |
| `OPENREPL_BACKUP_NAME` | Names this deployment (`default`) so that several share a bucket: backups are under `backups/<name>/`, snapshots under `homes/<name>/<home>/`. |

R2: endpoint `https://<account id>.r2.cloudflarestorage.com`, an API token with object read and write on the bucket. Without the four settings nothing is stored and the server behaves as before.

## 3. `objstore`

A client with the standard library only (like `persist/firestore.go`): AWS Signature V4 (`sigv4.go`, checked against the example of the AWS documentation and against a real RustFS), path-style addressing, `Put`, `Get`, `Head`, `Delete`, `List` (follows the pages; a listing past 20,000 objects is an error, never a silent cut), `Check`. A 5xx, a 429 or a lost connection is tried again three times. Whole objects only: no multipart (a backup is a few MB, a workspace is limited to 50 MB; a `PutObject` is atomic: it shows only when it is complete). `Fake` (`fake.go`) is a bucket in memory that checks the signature, for the tests of the three packages.

## 4. Backups (`backup`)

- **What:** every `*.db` file, `settings.json`, `admin-audit.jsonl`, `admin-stats.json` and `admin-usage.json` of `/opt/gotty`, as one gzipped tar with a manifest (sizes and SHA-256). When MongoDB or Firestore holds the databases (`persist.Remote()`), the `*.db` files are the server's local copy of them (LLD 05) and are backed up as a second copy of the remote data; the settings are not in a file then. A restore onto an empty disk puts back only the audit log and the totals in that case (`backup.RestoreFiles`): the remote database wins, and a copy on the disk is not a sign that the disk was not wiped.
- **A database is copied safely:** each file is copied to a temporary folder, the original must not have changed (size and modification time) while it was copied, the copy must begin as an unqlite file does, be a whole number of pages and be readable record by record; if not, the run tries again (three times, a second apart) and fails with "copied in the middle of a write". unqlite opens a file that is not a database without a word, so opening alone proves nothing.
- **When:** a recurring job (`utils.Jobs`, "Backup to object storage") every 15 minutes, the first one two minutes after the start, only when the fingerprint of the files (names, sizes, times) changed since the last upload; and once more at a clean stop, after the databases are closed.
- **Layout:** `backups/<name>/<UTC time>.tar.gz` (the SHA-256 in its metadata) and `backups/<name>/latest.json`, written last: a backup that dies on the way is never what latest names.
- **Retention (`Prune`):** keep the newest archive of each of the last 24 hours and of each of the last 7 days (UTC), the newest 3 and the one latest names (about 31 archives at most). It runs after each good upload; it never runs on a listing that could not be read whole; the first run of a process only logs what it would delete.
- **Restore:** `backup.Default.RestoreIfEmpty` runs at the start, before any database is opened (`common_setup`), when none of the files a backup holds is in the folder. It takes the archive latest names if its hash matches, else the newest of the others that opens (three are tried); extracts it into a folder of its own (`.restore-*`) and moves each file into place, never over a file that exists. Nothing usable is an error that is logged. **When the databases are files** (no MongoDB or Firestore chosen) **the server then exits** (`persist.Fatal`, status 4) instead of starting on an empty disk with no accounts, blog or settings; `OPENREPL_DB_FALLBACK=files` starts it anyway. With a remote database it goes on, since only the audit log and the totals were at stake. A disk that is not empty, or a bucket with no backup yet (a new deployment), is not an error. The order is: choose the database (LLD 05), then this restore, then open the databases.
- **Not in a backup:** `jobfile` (the waiting guest-folder removals; saved by its own job), `wsync/` records, the logs.

## 5. Workspace snapshots (`homesnap`)

- **Who:** the node that is the authority for a home: a single server, or the gateway (which holds a copy of every home, LLD 12). Never a worker (`homesnap.Default.Enable()` is not called in worker mode; workers have no keys). Only signed-in users' homes: `guest-*` are never kept.
- **Registered by use:** `touchHome` (`server/identity.go`) and the gateway's `PrepareHome` call `Touch(home)` when a signed-in user's request resolves its home. The first time a home is touched in a process: if its folder is missing or empty it is restored (below); from then on it is followed. A home that nobody touches is not asked about again.
- **Snapshot (`SnapshotHome`):** a job every 5 minutes snapshots the followed homes whose fingerprint changed and in which nothing was written for 30 seconds; at a clean stop every changed home, without waiting. A snapshot holds plain files and folders (empty ones too), never a link, a socket or anything named `.wsync-*`; a file over 50 MB, or one that changes while it is read, is left out and noted in the manifest; a home over 100 MB is not snapshotted (an error in the job's result).
- **Storage (changed 2026-11-13):** one object for each UTC day, `homes/<name>/<home>/<home>-<YYYY-MM-DD>.tar.gz` (`daily.go`), overwritten by every snapshot of that day (metadata: `sha256`, `generation`, `created`), and `latest.json` (generation, key, SHA-256, writer). The newest 3 days are kept (`Keep`). Where the bucket keeps versions (Backblaze B2 does, R2 does not), the older versions of a day's file stay in the bucket until its lifecycle rule removes them, and the profile page lists them (`objstore.ListVersions`, `GetVersion`). Objects of the earlier scheme (`<generation>-<time>-<writer>.tar.gz`) are still read and are removed when older than 3 days and a day's file exists. **Versions (2026-11-14, `homesnap/versions.go`):** a versioned bucket (B2) keeps every version an overwrite replaces, which with a snapshot every few minutes is dozens of copies of one day's archive, all billed. After each snapshot of a home, `pruneVersions` lists the versions of the home's files (the days' archives and `latest.json`) and removes for good (`objstore.Client.DeleteVersion`) all but the newest version of each file and, of the older ones, the last version of each clock hour (UTC) of the last 6 hours (`VersionHours`); delete markers are never removed. The thinning is not only of today: it takes in the versions that piled up before it, at the next snapshot of the home. A store that keeps no versions (R2), a failing listing, or an application key without the right to delete files (B2: "Read and Write" has it) leaves everything as it is, and the log says so. The profile page's list of earlier versions of a day therefore shows at most the newest and one a clock hour for six hours.
- **Two writers** (an overlapping deploy): the writer first looks (HEAD) at the day's file and gives up (`ErrConflict`) when it holds a generation not older than its own; it reads latest before and again after its upload and gives up too if the generation moved, so the pointer is only ever moved by a writer that was the newest. Without conditional writes this is a check, not a lock: a race inside the few milliseconds between the checks and the write can still happen, and then costs one version of the day, never a damaged file (an object is whole or not there).
- **Restore (`Ensure`):** `latest.json`, the archive, its hash, `Extract` (a path that leaves the folder, a link, a file the manifest does not list, a wrong size or hash: refused and nothing is written), into `.restore-<home>-*` and a rename onto the home. A damaged latest falls back to the newest good one (three tried). The sync engine is untouched: after a restore the gateway attaches the home to the worker as always and its three-way compare keeps the worker's newer files. The sync record is not part of a snapshot, so the first round after a restore treats every path as new and decides by modification time (LLD 12, "Three-way comparison").
- **A snapshot that does not match its manifest (2026-11-13, found in a log after a deploy: `.bash_history does not match its manifest`, four tries, no restore):** `newestValid` reads each candidate as a restore would (`verify`) and passes over one that fails for the next older. When every readable candidate fails, the newest of them is restored as it is (`extractForced`: the manifest is not held against the files; the path, link and size checks stay) and the log says so, rather than leave the home empty.
- **A snapshot the user picks that fails the manifest check:** `Restore` restores it as it is (`extractForced`) and answers `forced: true`, which the page shows as a note. Before, the failure came back as "The object store did not answer" (every unknown error does), which hid the cause; an unreadable snapshot now answers 422 "cannot be read as a whole" (`ErrBadSnapshot`), and the real error is in the log line `profile snapshots:`.
- **When a home is put back (changed 2026-11-13, after a deploy lost a user's files):** when its folder is missing, empty, or holds only entries whose names begin with a dot (`madeByTheServer`: the `.bashrc` that a terminal writes, the histories of the REPLs, `.tmp`). Before, any entry at all counted as "the home is there", so a new home with a `.bashrc` was never restored and its next snapshot took the place of the good one; with 3 kept, three small snapshots pushed every good one out. When the snapshot comes back over such a folder (`mergeInto`) a name that is in both takes the snapshot's version and a name only in the folder stays; a folder with any file of the user's is left alone.
- **A restore that fails is tried again:** `Touch` marks a home as looked at only when the restore has answered (restored, or truly nothing to restore). After an error the next request after a minute tries again, up to 10 times (`restoreRetryAfter`, `maxRestoreTries`), one log line each; then it gives up for the process. Before, the mark was set before the attempt, so one timeout of the object store right after a deploy was the last try. While a restore has not answered (`pending`) no snapshot of that home is made (note "waiting for its restore"): what is on the disk may be a fresh folder.
- **The time between snapshots** is a site setting (admin, Settings, "Workspace snapshots", `snapshotIntervalMinutes`, 1 to 60, empty: 5), applied at once to the running job (`SetInterval`: the job waits afresh with the new time).
- **The user's own list and way back (`restore.go`, `server/profile_snapshots.go`, the "Workspace snapshots" card of the profile page, `js/profile-snapshots.js`):** `GET /profile/snapshots` lists the bucket's `homes/<name>/<home>/` for the home of the signed-in account: each day (`id` `d:<day>`, kind `day`, `at` its last write, size, "newest", "few" for a file under a fifth of the size of the day before, a hint only), under it `earlier` (versions of that day's file, id `d:<day>@<versionId>`), the removed days that the store still holds (kind `hidden`) and the objects of the earlier scheme (`g:<generation>`). `POST /profile/snapshots/restore` takes `{id, mode}`, `mode` "folder" (the files go into `restored-<time of the snapshot>[-n]` in the home, nothing else is touched) or "replace" (also `confirm: "REPLACE"`: the snapshot is extracted beside, every file gets the time of now so that the sync with a worker keeps it as the newer, the old home is moved away and the new one renamed in, then the old one removed). A replace saves nothing of the files that are there (owner's decision 2026-11-13: the page tells the user to copy or download them first). `GET /profile/snapshots/zip?id=<id>` sends the files as a zip. The home is never named by the request; a POST must be JSON from the same origin; one restore a minute for a home (`ErrTooSoon`) and one at a time (`ErrBusy`).
- **Live map (admin):** the Persistence panel has an "Object storage" box (status of the bucket, the last backup, the workspace snapshots and the interval in its rows; off when none is set up). It also says **how much the bucket holds**, counted from the store's own listing (`objstore.Client.Usage`, in `objstore/usage.go`: it reads the listing page by page and sums the sizes of the objects under the server's prefix, plus the older versions a versioned bucket such as B2 keeps and bills, from the versions listing when the store gives one; at most 300 pages of 1000, and then it says "at least"). The count is made in the background (`server/object_usage.go`), kept for 30 minutes, made again when the bucket or its keys change, and the box says "counting what the bucket holds" until the first one is done. The line under the box starts with the total ("660.0 MB stored"), and the "Stored" row has the live size, the number of objects and the older versions.
- **Cost of a request:** one in-memory check after the first time; a home that has no snapshot is asked about at most once in ten minutes.

## 6. Dashboard

Health: "Object storage" (a request to the bucket at most once a minute), "Backups" (last one, size, files, archives kept, and that the files were restored at start), "Workspace snapshots". Jobs: "Backup to object storage" and "Workspace snapshots", with their last run and result (LLD 13). API keys: "Object store key id" and "Object store secret".

## 7. R2 limits (checked 2026-11-01) and what this uses

Free each month: 10 GB of storage, 1 million class A operations (put, list, copy), 10 million class B (get, head); deletes and downloads are free. Backups: at most 2,880 runs a month, each 1 archive put, 1 pointer put and 1 listing (about 8,600 class A, 0.9%); the storage is about 31 archives. Snapshots: a few per active user a day. Storage, not operations, is the limit: 200 users with 5 MB workspaces kept 3 deep is about 3 GB; if every one filled the 50 MB limit it would pass 10 GB.

## 9. Limits and ideas

- A snapshot is of the gateway's copy: files a worker wrote and has not yet sent are not in it.
- The sync record is not snapshotted (section 5).
- No multipart: an object is one request (the largest is about 100 MB).
- A deleted account's snapshots are not removed yet.
- Backups are not encrypted at rest by the server (the bucket's own encryption applies); the workspaces may hold anything a user wrote.
- Not built: logs in the bucket, a restore button in the dashboard, conditional writes for the pointer (R2's support to be checked).
