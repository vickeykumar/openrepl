# 19. Genie agent and chat: efficiency, credits and plans

Built on branch `feature/genie-agent-efficiency`. The plan and the screens it was built from were on the design canvas "Genie Agent End Results". This document says what was built, where it lives, what it costs and what is not built.

Related: 07 (the `/chat/completions` proxy and the usage line), `docs/agent-mode-design.md` (the agent's protocol, permissions and Stop), 13 (admin).

## 1. The usage record, credits and plans (phase 0)

Every answer of a model is one **usage event**: counts only (tokens, credits, model, task and step), never a question, an answer, a file or code. `server/meter.go` is the one place.

- **Credits.** One credit is a tenth of a cent. A model's credits for a thousand tokens come from `GenieSettings.CreditWeights[model]` (sent, written), else from its `ModelPrices` (a dollar for a million tokens is a credit for a thousand), else from the cost the provider reported (OpenRouter), else 0. `creditsFor`.
- **Where it is counted.** `chatproxy.go` calls `noteMeter` next to `tokenTotals.add`, after the answer was sent. A step of a task is keyed by task and step (`meterLedger.seen`), so a counted step is not counted twice. A step the provider failed has no usage and is not counted.
- **Where it is stored.** The same database as the token totals (`genie_usage.db`, `tokens_db_handle`), under `m:<key>`; `meterRecord` holds this month's credits, steps, tasks and chat answers, and the all-time credits. The record also holds an optional `Plan` of that person. Counts for the admin ("How the agent is doing") are one record under `m:stats` (`agentStats`).
- **The plan.** `entitlementsOf(g, uid, admin)` is the one place that says what a person may do: credits for a month (0: no cap), credits for one task (0: none), the steps of a stretch, tasks an hour. The default plan is `GenieSettings.PlanName/PlanCredits/PlanBudget` with today's limits for the rest; a person's own plan (`planRecord`, set with `POST /admin/genie-plan`) replaces the numbers.
- **Shadow mode.** The record is on unless `MeterOff`. Nothing is charged or limited until an admin turns `CreditsOn`; users then see credits (`creditUsage` in the `X-OpenREPL-Usage` header and `GET /chat/usage`), a used-up month refuses with `credits_exhausted` (429, before a task is taken), and an admin is never limited. Guests keep their fixed request allowance and have no plan.
- **A task's own credits.** `agentTask.credits`; `GET /chat/usage?task=<token>` returns them for the user's own task.

Admin (`admin.js`): "Usage record and credits" in Site settings (switches, plan name, credits a month and a task, a weight per model next to the prices) and "How the agent is doing" in Genie usage: counts since the server began, and a baseline the admin records before a change. `GET/POST /admin/genie-measures`, `POST /admin/genie-plan`.

## 2. Sending less (phase 1)

`agent-task.ts` (plain code, tests in `test/agent-task.test.ts`):

- `compactHistory`: the last two results and answers of a task stay whole; older results are one line each (what each action did, not its output) and older answers lose the code they wrote. The first message is never touched; the page keeps the whole history.
- The editor and terminal text goes in every request, as the last message. (It was sent only when it changed, with one line saying "the same as before" otherwise; but an earlier context is not kept in the messages, so a step after a read-only step had no editor text and the model asked the user to paste the code. Removed 2026-11-17.)
- Chat (`chat-send.ts`, `messagesToSend`): older answers lose the middle of long code blocks, and the editor and terminal text is not sent twice (the history already holds it at each message).

## 3. The task card (phase 1)

- **Plan.** The model sends `"plan": [...]` in its first step and `"plan_done": [n]` later (`parseStep`, `PlanState`). The card shows it above the steps.
- **Check before done.** `WorkTrack` follows accepted changes (`editor_write`, `editor_insert`, `editor_replace`) and what ran after them (`run`, `debug`, `bash`, `terminal_type`). A step that says `done` after a change that was not run is sent back once (not at the last step); a change after a check is a fix attempt, two at most while a check is known to fail (the page refuses a third edit and tells the model to say what fails). The card ends with Checked or Not checked, what changed (lines added and removed against the editor before the first change), and the steps, time, tokens and credits used.
- **Batching.** A prompt rule: independent reads in one step, up to three actions.
- **Lenient reader.** `extractJSON` mends a trailing comma, a comment and a BOM when an answer cannot be read as it is (it already took a fence and text around the JSON).
- **Outcomes.** The page reports how a task ended (`POST /chat/agent-outcome`: done, stopped, failed, unreadable, toolong; whether it changed code and checked it) for the counts in section 1. The server counts a task once, for its own user.

## 4. Editing a part and looking around (phase 2)

- `editor_replace` (`old` and `new`, or `start_line`, `end_line` and `new`): the page builds the file with that one part changed and goes through the same review as `editor_write` ("Genie wants to change this part of the file"). An `old` that is not found or is found twice is refused with the reason.
- `files_search` and `files_read`: read-only, no permission question. `POST /agent_files` (`server/agent_files.go`, execution-bound in the gateway like `agent_bash`): owner of a signed-in workspace only, paths relative to the workspace with no hidden name and no link out of it, text files up to 1 MB, 5,000 files and 4 seconds for a search, 40 matches, about 90 lines (3,600 characters) for a read with `next_line` to go on. It reads the file as saved on disk.
- Chat: **Apply as diff** under a code block that starts with a definition (`js/src/page/lib-region.mjs`): the definition is found in the editor by name and only that part is proposed.

## 5. Carrying on, notes and undo (phase 3)

- **Carry on.** The steps of a task are a stretch (the admin's `agentMaxSteps`, at most 8). When a stretch is used and work is left, the card pauses and asks. Yes sends `agent_carry`: `agentLedger.nextWith` starts a new stretch (steps count from 1, the task's own count and credits go on, the 15 minutes start again), at most three times (`maxAgentCarries`). The ceiling is never raised.
- **Budget.** With credits on and a plan with credits for a task, a step that would pass it is refused (`agent_budget`, 429) and the page asks; yes raises the task's budget by one more budget (it counts as a carry).
- **GENIE.md.** Read at the start of a task through `files_read` (first 80 lines, 1,500 characters at most), sent as hints inside the first message of the task. It adds up to that many characters to every step.
- **Undo this task.** `AgentRunner.undoTask`: each file the task changed is put back as it was before the first change, through the editor's own history, when nobody changed it since the task; a file that was open before is opened again. Files the task created are left.

## 6. Streaming and native tool calls

- **Streaming** (admin switch `StreamAnswers`, off by default). `sanitizeChatBody` keeps `stream` only when the switch is on and the model's host reports usage in a stream (not Cloudflare Workers AI). The proxy flushes each piece (`copyFlushing`; `logResponseWriter.Unwrap`). The page reads events (`sse.ts`), draws a chat answer as it grows, and shows the words of an agent step (`partialSay`) in the card while the JSON is written. A chat answer is told to the others of a shared session when whole. The 4 MB cap and the usage count work as for a whole answer.
- **Native tool calling** (admin switch `AgentNativeTools`, off by default, and a list of models, `NativeToolModels`). For a model on the list an agent step is sent with one function `step` whose parameters are the step object, the call forced and the JSON mode left out (`agent_tools.go`); the page reads the arguments of the call exactly as it reads the text. Until an admin saves a list, the list is the OpenAI models (`nativeToolModels`); the admin ticks one box for each model in Site settings, and an empty list is a choice (no model).
  - **Fallback.** If the host refuses a call that carried the tool (HTTP 400 or 422, or an error whose text is about tools or `tool_choice`), the proxy sends the same request once more as text JSON (`plainBody`: no tools, `response_format` json_object unless the model is `NoJSONMode`) and remembers the model as "no tools" in memory for an hour (`toolMemory`), so later steps skip the failed try. The user sees no error. The refused call is not an answer: no usage event, no step counted, no request charged (the first step's charge happens once, for the answer that came). Any other error (429, 5xx without tool words) is shown as it always was and is not remembered. A host that accepts the call and answers plain text needs nothing: the page reads both.
  - **Counts.** `agentStats` keeps the tries (`toolTries`), the refusals that went again as text (`toolFallbacks`) and the refusals of each model (`toolRefused`); Genie usage shows them in "How the agent is doing".

## 7. Not built, and limits

- One plan per person is stored and read, but there is no screen to set it yet (only the admin API).
- No balance or payment: credits are counted and can limit, nothing is sold. Two tabs spending at once, a server that restarts in the middle of a task and several gateways are not settled (the ledger of tasks is in memory, as before; the credits are stored).
- "Review changes" on the finished card (canvas) is not built: the review of each change is the one that was shown when the change was made.
- Streaming and native tool calling are not tried against the real providers in this change (the fallback is tested with a fake host that refuses the tool).

## 9. Chat history and chat tabs

Built after the design on the canvas "Genie Chat History". A chat is saved in its owner's own workspace, so it lives as long as the workspace does and follows it (snapshots, other devices); no server database holds anyone's conversations.

- **Files.** `.genie/chats/<id>.jsonl`, one JSON Lines file for each chat, and `.genie/tabs.json` (`{"open":[ids],"off":bool}`). A line is one thing that happened and lines are only added: `meta` (id, created, context `chat` or `practice:<question>`), `title` (the last wins), `state` (mode, model, effort; the last wins), `user`, `answer`, `task` (counts and names, no content). A line cut short by a crash is skipped when read. The files are plain ASCII (every character above 127 is written as `\uXXXX`, `asciiJSON`), so an editor that does not read UTF-8 shows no garbled text. The Files panel shows a folder whose name starts with a dot but not what is inside it (files or subfolders; `07-file-browser.js`, `preprocessnodedata`), so `.genie/` is listed and its content is not. The editor and terminal text read for an answer is not saved. Export as Markdown is a view of the file, made by the server.
- **Server** (`server/genie_chats.go`, `POST /genie_chats`, execution-bound in the gateway): `state`, `read`, `append`, `tabs`, `off`, `delete`, `deleteAll`, `export`, `exportAll`. Only the owner of a workspace (a shared session's viewer names the owner's workspace and is refused, `not_owner`); guests have a workspace too unless `ChatHistoryNoGuests`; the whole feature is off with `ChatHistoryOff`. Lines are checked (kinds, allowed keys, 64 KB a message, 20 lines a call), the folder and its `chats` folder must be real folders of the workspace (checked before anything is made, so a link out is never followed), `tabs.json` is written whole and renamed into place. Limits (admin, Site settings): 50 chats, 8 open tabs, 200 KB a chat, days kept (0: for ever). Over its size a chat loses its oldest messages and keeps its head; over the number of chats the oldest closed chat goes, never an open one. 240 calls a minute for a person.
- **Panel** (`chat-tabs.ts`, `chat-store.ts`, `index.ts`): a strip of tabs under the header (+, a ⌄ list of every chat with search and Reopen, a menu on right-click, double-click to rename, drag to move, middle-click to close; keys Alt+T, Alt+W, Alt+arrows, Alt+1 to 8, Alt+H while the panel has the focus). Each tab has its own conversation, its own mode, its own draft (kept in this browser) and its own recap of agent tasks. The messages of the tab that is shown are in the panel; those of the others wait in a fragment, so an answer that arrives for a tab that is not shown goes to its own tab and leaves a dot. A ring means a task is running there, an amber dot that it needs the user (a toast offers Go to tab), a coral dot that an answer is ready.
- **One task at a time.** A task works in the editor and terminal, so only one runs in a workspace: while a tab runs one, Agent is off in the other tabs (with the reason on hover) and Send does not stop it from there. Chat is free in every tab. Closing the running tab asks. When a tab is shown again and the editor has another file or language than the chat was about, a note says so.
- **Writing.** Lines go through a queue (`ChatStore`), in order; when the workspace cannot be reached they wait and are tried again (every 8 seconds, when the browser is online again, or `ChatWidget.retrySave()`), and the strip says "not saved right now". A viewer, a site with chats off and a person who switched saving off get a single tab and no strip. Signing in or out starts again from the other workspace's chats.
- **Profile page** (`js/profile-chats.js`): the number and size of the chats, "Save my chats", "Download all as Markdown", "Delete all chats" (asks once). **Admin:** Site settings, "Genie chat history".
- **Checked in the code:** a "fork" is a second terminal in the same workspace (not a copy), so there is nothing to leave `.genie/` out of; a guest's workspace is not the one they get when they sign in, so guest chats do not follow a sign-in.
- **Not built:** the admin's count of how many people have chats and the space they use (an admin cannot read a chat, and the counts would need a scan of every workspace); a chat per question on the practice page is saved with its `context` but the History list there is not filtered by it yet.

## 10. The IDE guide, small models and starter chips

- **The guide.** A small model said it could not read the terminal and answered "run it" with a description: the chat prompt was one line and the agent's rules never said what the page is. A fixed section now opens both prompts: the agent's (`ideGuide` in `server/agent.go`, before the answer format) and the chat's (`CHAT_IDE_GUIDE` in `index.ts`). It says that the editor code and the terminal text are given to Genie and can be read, what Run, a typed line and the language picker do, and has 4 worked examples (run, install, explain an error, change the code). In Chat it says to switch to Agent for anything that has to be done. Practice keeps its interviewer prompt without it.
- **Save after every edit.** Weak models left their edits in the editor only. The guide now ends with an explicit rule and a worked step: after every accepted `editor_write`, `editor_insert` or `editor_replace` the next step has `files_save`, and a task is never finished on an unsaved edit. The longer rule in the agent's list of rules stays; this one is shorter and comes first.
- **Replace that did not match.** `editor_replace` failed a lot with a small model: the old text was retyped with other indentation, or from an older version of the file. `locateOld` (`agent-protocol.ts`) tries an exact match, then one that ignores white space (accepted only when unique, and the range is the editor's own text). When nothing matches, the failure names the 3 editor lines that look most like it; after 2 failures in a row it says to send `editor_write` with the whole file. The guide says to copy 1 to 3 whole lines, never `...`.
- **What a task is sent (steps 1, 3 and 4 of the plan of 2026-11-17).** After the task: `Earlier in this chat` (the summary, if there is one, and the last 6 turns; `chatTurnsText`), a note when the editor is not what the chat was about (`staleForAgent`: switch the language and open the file first), `Workspace now` (`factsText`: language, open file, the file names only when the user has allowed the agent the files, the last error of the terminal; read from the page just before the task) and, for a request of two words or less like "try again" with nothing to explain it, `ASK_FIRST` (ask one question, do not guess). The note of the panel for a restored chat cut a file name at its dot; `staleParts` fixes it.
- **Summary of a long chat.** When the turns before the last 4 pass `Genie.SummaryTokens` tokens (default 6000, 1000 to 40000, four characters to a token; `SummaryOff` stops it; Admin, Site settings; sent as `genieSummaryTokens`; the editor and terminal text is not counted, it is in every request as it is), `maybeSummarize` (`index.ts`) asks the model in use for at most 1200 characters (`SUMMARY_PROMPT`, the old summary plus the turns that go in; no site context). It is an ordinary chat request: counted in credits and in the per-minute limit like any other, for guests too. The summary takes the place of those turns in the history, right after the editor snapshot (so every system message stays at the start), and is added to the chat file as `{"t":"summary","text":...,"steps":4}` ("the last 4 turns before this line were kept"). A reload restores the whole conversation on screen and sends the summary and the turns after it. A reply that is empty, a few words or JSON is not used (`cleanSummary`); the chat then goes on as before, and a failed try is not repeated until the chat has grown. Not summarized: the practice page.
- **The bar that waits, and the arrow to the last message.** `attention(true, {brief, card})` tells the panel what the task waits for and where its card is (a permission, the step limit, a change to review in the editor: no card). While the card of the shown chat is not in view (`cardView`, polled 2.5 times a second while a task waits), `renderWaiting` shows a bar above the input (`#chat-widget__wait`, a polite live region; the whole bar is one button); a click scrolls the card to the middle, rings it for 1.7 seconds and focuses its first button (`goToWaiting`; for a change in the editor it focuses the editor). The arrow (`#chat-widget__jump`, `updateJump`) shows when the conversation is more than 80 px above its bottom (`jumpVisible`; the conversation is `column-reverse`, so the distance is the size of `scrollTop`); one click scrolls to the last message. While the user reads further up, `noteRef` and a mutation observer keep the first shown message where it was (new lines do not move it) and count the new ones ("Latest · 3 new"). Reduced motion: jumps, no glide. Designed in the canvas "Genie: waiting for you banner".
- **A failed replace** now says at once to send the whole file when the editor has 80 lines or less, and lists the lines where an old text is when it is there more than once.
- **The Preview as a place to work (2026-11-18, LLD 17 section 13).** 15 actions `preview_*` (read, console, network, inspect, wait; click, type, press, scroll, select, hover, go, resize, eval, storage), a section "THE PREVIEW" in the guide of the prompt with 3 examples and the rule "WEB PAGES": after changing an .html, .css or .js that a page uses, reload the Preview and read its console and page before "done". The check-before-done rule counts `preview_console` and `preview_read` after a change as the check (`CHECKING`, `CHECK_BEFORE_DONE` says how). The starter chips with the pane open: "Test my page", "Check the console", "Make it fit a phone". Chat gets the chip "the preview".
- **Small models.** `isSmallModel` (`agent-protocol.ts`) tells one from its id: a size in it decides (40B or less is small), else mini, flash, lite, nano, tiny, small, and also free, auto and router (a router such as `openrouter/free` picks a model for each request and mostly picks a small one). In Agent mode with one the panel shows a note, and a Switch button when the admin has set an Agent model (`Genie.AgentModel`, Admin, Site settings; sent to the page as `genieAgentModel`; unknown or switched-off models are refused). It only suggests: nothing is switched by itself.
- **Starter chips.** An empty chat shows 4 chips for the mode (`starterChips`); a click puts the words in the box, it does not send. They go when the first question is asked.
- **Checked:** Go tests (`genie_guide_test.go`), widget tests (`isSmallModel`, `starterChips`), browser test (`genie-efficiency.spec.js`, chips and hint).
- **Not checked:** how much better a real small model answers with the guide.

## 11. A default model for Chat and one for Agent, the Agent list, and the ticks of an added model

- **Settings.** `DefaultModel` is the Chat model; `AgentModel`, `AgentModels` (nil: every model that is on may be used; a saved list: only those) and `AgentEffort` (default low) are new (`agent_models.go`, `settings.go`). `normalizeAgentModels` keeps known, switched-on, distinct models and the Agent model inside the list. `agentDefaultModelID`: the admin's choice if allowed, else the first allowed model that is not small, else the Chat model, else the first allowed. The page is told `genieAgentModel`, `genieAgentModels`, `genieAgentEffort`.
- **The server is the guarantee.** An Agent request for a model that is not allowed gets `400 model_not_for_agent` ("Model not supported for Agent mode. Choose another model.") before anything is counted or sent; an Agent step that names no model gets the Agent model (`withAgentModel`). The widget switches to the Agent default and says so.
- **The chip per mode** (`model-choice.js`): picks are kept per mode (`genie-model`, `genie-model-agent`); `setMode` swaps them and returns a note when the pick had to change. The model list shows a model that is not allowed in Agent mode greyed, tag Chat only. Practice questions use the Agent model; the New question dialog lists the allowed ones, a change is for the page only.
- **Admin.** Models and prices: card "Default models" (Chat model, Agent model, effort). Every model has its ticks in its own row of the Genie card (and of Added models): Starts in the short list, Agent mode, Available for guest users (an added model also has Small model). There is no separate Agent list card. Agent mode ticks: none saved yet means models that are not small start ticked, and an unrelated save sends no list. Guest ticks of built-in models are saved as `GuestBlockedModels` (the page gets `genieGuestBlocked`).
- **Ticks of an added model** (row in "Added models"): Small model (`CustomModel.Small`, nil: the id decides, `isSmallModelID`), Agent mode (one tick per model), Available for guest users (`CustomModel.NoGuests` for an added model, `GuestBlockedModels` for a built-in one; the tick is the opposite). `modelIsSmall` and `guestsMayUse` are the server rules; the page gets `small` and `guests` per added model. A guest who asks for a model kept for signed-in users gets `403 model_not_for_guests` ("Sign in to use <name>.") before it is counted. The picker lists such a model greyed for a guest, tag Sign in; a click shows "Sign in to use the complete features of Genie, including this model." (`MC.guestOk`, the body class `is-signed-in`).
- **Checked:** Go (`agent_models_test.go`), node (`model-choice.test.mjs`), browser (`admin-site-sections.spec.js`).
- **Not checked:** the greyed rows in a real browser on the live site; the guest refusal end to end with a real guest cookie.

## 12. The failure log, a stuck task, prompt groups, Review and Resume

Canvas: claude.ai/artifact/6NKLrHQDc5M1Jfo4YMp3QP (boards 1 to 7); the ideas list is `docs/genie-improvement-ideas.md`. Built 2026-11-19 on `feature/genie-agent-efficiency`.

**The Genie log** (`server/genie_log.go`). On the free plan (every user until a paid plan exists; each event carries `plan`) the agent reports `step_failed`, `stuck`, `retry` and `need_tools` events to `POST chat/genie-event` (a signed-in user only; 204 whatever happens), and the end of every task is written by `handleAgentOutcome` once per task (`task_end`: outcome, steps, seconds, failed steps, groups). An event is built by `eventFrom` from a whitelist, so a page cannot add a field: time, random page-session id, event, model (a model of the site or "other"), mode, step, action (an action of `agentActions` or "other"), file extension, a reason and its code (`reasonCode`: stale_ref, no_file_open, unreadable, edit_mismatch, ... a fixed list, else "other"), counts, outcome, groups, plan, prompt version, and, added after the first local logs (2026-11-19): `tid` (a random id of one task, to group the events of a page that ran several), `rule` of a stuck task and the user's `choice` after it (event `stuck_answer`), `trail` (names of the last actions, only names of known actions), `tokens` of a task, `lang` (the picker's language). Prompt version g2. The reason is cut at 200 characters and scrubbed by `scrubReason` (quoted text, addresses, long tokens, credentials and anything path-like or file-name-like replaced); the page sends `safeReason`, which for what runs the user's program or reads their page is a few words ("exited with an error"), and for anything else the first line only (the editor's message holds lines of their code after its first line). Never held: the user, the task or any message, file contents or names, terminal or page text. A command that exits with an error is a check that failed, not a failed step, and is neither logged nor counted as stuck (`isCheckFailure`, `isLimit`).

Stored as one JSON object per line in `/gottyTraces/genie/events-YYYY-MM-DD.jsonl`, a file for each day (20 MB at most; what is refused is counted), days older than the setting (`genieEventDays`, 30 by default) deleted. A user may report 600 events an hour. The switch `genieEventsOff` (site settings, Genie, Agent mode card) stops the page sending and the server keeping. Admin: System, Genie log (`GET admin/genie-log?days=&model=&event=&action=&q=`: tasks, done %, stuck, failed steps, worst action, a table by model, the newest events; `?download=1` sends every event of the days as `.jsonl` and writes the audit log). The privacy page, the FAQ, the notes and the about page say what is recorded.

**The gotty log download** (`GET admin/logs?download=1`): the whole file, line by line through the viewer's masking, as `openrepl-gotty-log-<date>.txt`; audited.

**A stuck task** (`genie-events.ts` `StuckDetector`, `agent.ts` `onStuck`). The agent tries other ways first; the task is paused before the next request, so nothing more is used, in three cases. (A) The same step (action and target) failed 3 times in a row, or (B) 3 steps in a row failed with the same words (numbers ignored): a step that worked in between, whatever it was (reading the page again is another way), starts the count again. The design said two in a row for B; with two it fired before a model could follow the hint a failed step carries. (C) 6 steps in a row that changed no file and printed nothing the task had not had before (`freshOutput`). (D) Once per stretch of 15 steps or more (with the usual 8 the pause at the step limit comes one step later anyway), when 80% of the steps are used and the task has changed nothing at all. C and D may be a task that only looks around, so their card also has **Keep going**. A command that exits with an error, and a limit the model was told of, are not failures. The card offers Try with a stronger model (the first of the admin's list `genie.escalationModels` that the user may use and is not on; it has 5 steps, is told in one request what failed, then the user is asked to keep it or go back), Give a hint (the failure goes in the chat box; the task ends as stopped) and Stop. The user's own "no" to a card is not a failure.

**Looking steps and the reason a part is gone** (2026-11-19, after the first logs of prompt g2). A step that only looks (`isLooking` in `genie-events.ts`: `preview_read/console/network/inspect/find/state/wait/storage`, `files_list/search/read`, `read_output`) no longer ends a run of failures, so a model that reads the page before each retry of a failing click reaches rule A on the third failed click. The bridge `gone()` (`livepreview/bridge_cmd.go`) answers with `why` and a text that says which of three cases it is: `never` (no `preview_read` of this page gave that number: a reload or another page), `renamed` (a part of the same kind is at that place; the text gives the old and the new name) or `removed` (none of that kind is left). `previewFind` passes that text on to the model, `reasonCode` turns it into `stale_ref_reload`, `stale_ref_renamed` or `stale_ref_removed` (and `stale_ref` for the rest), and the server whitelist `genieCodes` keeps them, so the Genie log tells which one a game causes.

**Prompt groups** (`server/agent.go` `agentPromptParts`, `agentSystemPromptFor`; page: `agent-groups.ts`). Every line of the prompt has the group of actions it belongs to: core (4 actions, `need_tools`, `finish`, the rules and the JSON), editor, files, terminal, preview, store. The page sends `agent_groups` with each request (the words of the task, the page and the terminal decide; a group that came stays); the server drops the field before the host sees it, and without it every group is sent as before. A model asks for a group with `need_tools`; its actions are in the prompt from the next step. The prompt is 24,825 characters with every group and 6,446 with the core only (measured in `TestThePromptWithoutGroupsIsShortAndSaysWhatToAskFor`). The tool schema's enum still lists every action. Tests keep the table of groups, the actions list and the page in step. Whether it helps is read from the live pass rate in the Genie log, not assumed. The prompt of a task changes only when a group is added, so the prompt cache of a task is not lost between its steps.

**Review all changes** (`review-changes.ts`, `agent.ts` `renderReview`, page script `35-genie-changes.js`; canvas "Genie: Review above the box", built as recommended). A bar above the chat box (`#chat-widget__review`), the slot of the waiting and Resume bars. While the task runs it is one line with a count and Show; when the task ends it lists every file changed (from the before and after copies the task keeps), what the Files panel did (made, renamed, moved, deleted to the Trash, deleted for good, pasted) and what shell commands did (below), each with its lines, Keep and Undo. Keep or Undo settles a row and it **vanishes**; when the last goes the bar goes and the chat says "Reviewed N: a kept, b undone". Undo puts a file's text back unless it was changed since (the row then says so and stays), takes a made file to the Trash folder, turns a rename or a move back; a file deleted for good and a paste have no Undo. Undo all asks first. A new task, or another chat tab, hides the bar; what was not settled counts as kept. The task card keeps its chips and Undo this task, not a list.

*In the editor itself.* Clicking a path opens the file (`host.files.open`) and `GenieChanges.show` (35-genie-changes.js, `lib-changes.mjs`) marks it: a green Ace marker on each added line, the removed lines as Ace line widgets (red, struck through, not editable; below the line before the change, and moved up into made room at the very top of the file), and a thin bar at the top of the editor with the title, +added −removed, k of N, ‹ ›, Keep and Undo (Restore and Dismiss for a deleted file, which has no text in the editor: its old text is shown read-only over it). The bands are worked out from the text before the task and the text the editor holds now, again after each edit, so they follow what the user types. Keep and Undo there are the bar's. A rename, a move and a file made empty have nothing inside to show.

*What shell commands changed* (`server/agent_shell_changes.go`). The server looks at the workspace before and after each `bash` command (hidden names, caches and the Trash folder are left out; more than 4000 files is not followed and the page is told): the files that are new, changed or gone come back in the result with the text of the small ones (32 KB each, 768 KB in all, at most 40 changes). The page merges commands that touch the same file (first text before, last text now; made and deleted again is nothing). Undo of a changed or deleted file is `POST agent_restore`, which writes the text back only if the file is still as the command left it (409 otherwise), inside the workspace, text of at most 64 KB; a made file goes to the Trash folder. A file too large to keep a copy of is listed without Undo.

**Resume** (`chat-tabs.ts` `Interrupted`, `index.ts` `renderResume`, `server/genie_chats.go`). A running task writes a `checkpoint` line to the chat file at its start, after each step and at its end (`outcome`: running, done, failed, stopped); the server keeps only the newest checkpoint of a chat, so a long task does not grow the file. A chat whose last checkpoint says running and is under a day old shows a bar above the box: Resume this task starts a new task ("Continue: ...") that is told it was interrupted and looks at the workspace as it is. The steps of the old task are not kept, so this is a new task and not a replay.

## 24. Connections: tools on other services through MCP (2026-11-20)

Canvas: claude.ai/artifact/6Vz7UqKMMPXYPJ4Zwq3w9G, boards 5 (MCP), 6 (safety), 8 and 9 (a plugin from a link, the switch and the request flow). Phase 3 of the design: GitHub first.

**The server is the client.** `server/genie_mcp.go` speaks MCP over streamable HTTP: JSON-RPC 2.0 by POST (`initialize`, `notifications/initialized`, `tools/list` with paging, `tools/call`), answers as JSON or as a `text/event-stream` (the message with our id is picked out), `Mcp-Session-Id` echoed, `Authorization: Bearer <token>`. Every call goes out through `newExtClientFor`, the client of the plugin links: public addresses only (checked at the moment of connecting, so a name that points inside is refused), https, no proxy, 30 s. A browser page never talks to an MCP server: it cannot keep a token out of reach of its own scripts, and most servers refuse a page.

**Connecting.** `genie_conn.go`. The catalogue the site ships is data (`connectionCatalogue`: GitHub, `https://api.githubcopilot.com/mcp/`). Connect takes a token the person pastes (a GitHub personal access token): the shape is checked, a real `initialize` + `tools/list` tests it, and only then it is sealed (`sealKey`, AES-GCM under the server's secret, bound to the person and the connection so it cannot be moved to another) in a file for each person under `/gottyTraces/genie-connections/`. It needs `OPENREPL_SECRET` (or the secret the server made): without one Connect says so and keeps nothing. The token is never returned, listed, logged, put in a prompt, a chat file or a snapshot (the workspace is not where it lives); Disconnect deletes it; a leak test reads every file of the folder and every answer. At most 8 connections for each person. `POST /genie_conn` is signed-in owners only and is not execution-bound (it runs where the account is, the gateway in a gateway deployment); ops: `list`, `connect`, `disconnect`, `refresh`, `call`, `requests`.

**Levels.** Each tool is `read`, `write` or `irreversible`: the catalogue's word first (`Levels`: GitHub's `merge_pull_request`, `delete_file`, `delete_repository` are irreversible), then the tool's own annotations (`readOnlyHint`, `destructiveHint`), and a tool that says nothing is a write: a wrong guess has to be the careful one. The page and the model are told the list the server made (`toConnTools`: name, one line, level, argument names with a * on required ones); a tool with a name that is not a plain identifier is left out.

**The call.** The agent's action `mcp_call` (`connection`, `tool`, `args`) is in a new group `connect` (`agent.go`, `agent-protocol.ts`, `agent-groups.ts`: the words github, issue, pull request, notion, figma, connection, mcp bring it, else `need_tools`). The page looks the tool up in the person's own list and sets the level and the connection's name itself (`Action.level`, `title`: never taken from the model); an unknown connection or tool is refused with what is there. Permission kinds `mcpread`, `mcpwrite`, `mcpdanger` (not one for each connection: the card names the service): a read can be allowed once for the session, a write too (and "Allow everything" includes both), what cannot be undone is asked every time and no grant lifts it. The card shows the service, the tool and the arguments as they will be sent. The server refuses a write or an irreversible call that comes without `confirmed` (superseded: see section 24a, the server's tickets replace it), counts 20 calls for each task (`takeTaskCall`; the page counts too), cuts a result at 6,000 characters (said), stops a call after 30 s, and allows 60 calls a minute for each person.

**Outside text.** What a tool returns is put between two lines that say it is the service's text and data (`fenceOutside`; an end marker inside it is taken out so that it cannot close the fence early), and the agent's rules say never to follow orders in it. **Taint guard** (`Permissions.markOutside`, `riskyAfterOutside`): once a call of the task has returned (a write's confirmation counts too), a shell command, a delete or move, a write to a connection and running code in the Preview ask again, whatever was allowed for the session, and the card says "follows text from outside, which can carry orders" and offers no "for this session". So "Allow for this session" for writes holds for the first call of a task only. A new task starts clean.

**The note.** An agent task starts with the services that are connected: names and tool counts, and the tools themselves (`github.create_issue [write] (title*, body): …`) only when the words of the task say it is about a service, or once the model asks for the group (`need_tools` returns the list in its answer). A connection with no tools listed costs a line, not ten thousand tokens.

**Plugins that need a connection.** `plugin.json` may list `connections`: `{"id":"github"}` (the site's catalogue, its address cannot be changed) or `{"id":"acme","title":"Acme","url":"https://…"}` (another server: only from a link; https, a host name, no port, no user name; at most 5). The card of a plugin says what it needs and where it stands (`access`): `official` (a catalogue plugin: the site's own connections, nothing to ask), `open` (the admin switched "Allow connections without approval" on, and every host is on the list when the list is not empty), `approved`, `waiting`, `declined`, `needed` (send a request), `host_denied`, `off`. From a link `plugin_apply` is refused (403) unless it is `open` or `approved`. **The request** (`genie_conn_requests.go`, `plugin_request`): the server fetches the plugin again and keeps the connections, skills, link and digest it saw (never what the page says); the same digest waiting twice is one request; at most 10 waiting for a person; the admin approves it for the site or for one person, or declines with a reason; an approval holds for that digest, so a changed plugin goes back to review. An approved connection of another address becomes one the person can Connect (token as above); the host list is checked again at Connect. The catalogue plugin **GitHub workflow** (open-issues, file-issue, pr-draft; actions `mcp_call`) is the example that works end to end.

**The page.** `/add-plugin` has two more tabs: **Connections** (each service with its state and its tools in grey for reads, yellow for writes, red for what cannot be undone; Connect opens a password field that is cleared once sent; Disconnect) and **Requests** (the person's own, with the reason when declined). The install card shows the connection and its server and, when it needs approval, a note field and Send request instead of Install.

**Admin.** Site settings, Agent: card **Connections** (switch for the whole feature, "Allow connections without approval", "Only these servers": one host for each line) and card **Connection requests** (the waiting ones with the files' skills, the link, the servers and the note; Approve for everyone / for this user / Decline with a reason; who is connected to what, never the tokens; the last calls). Calls are recorded (`calls-<day>.jsonl`: the connection, the tool, the level and the outcome, never the arguments or the result). Settings changes and each answer go to the audit log.

**The guide.** `genie.html` section `#connections` (in the contents list) with four GIFs (`guide-connections`, `-connections-agent`, `-connections-request`, `-connections-skill`) recorded by `e2e/tools/record-connections-gifs.spec.js` with the IDE maximized and Genie pinned, a FAQ entry and a knowledge note.

**Not built (from the canvas):** OAuth (built the same night, see section 24a), connections other than GitHub (Notion and Figma are not in the catalogue yet; an admin can approve a plugin's own server), one permission kind for each connection ("GitHub reads", "GitHub writes"; here there are three kinds for all), the Ask, Safe auto and Full auto presets (they do not exist yet), a skill's source in the card of the task, the failure log's own fields for connections (a record of its own is kept instead), a local MCP server in the user's own sandbox, and tokens that follow a person across several servers (they live where the account is handled). If the server's secret changes, saved tokens cannot be read: connect again.

Tests: `genie_conn_test.go` (the MCP client with JSON and event streams, the levels, connecting with a good, a bad and a malformed token, the leak test over every file and answer, sealed for one person only, Disconnect, the fence and the 6,000 cut, a write without its card, 20 calls for a task, the record without arguments or results, the switches, the list of servers, a plugin's connections read and checked, a catalogue plugin, the request flow with approve for one person, for the site, decline and a changed plugin, `open` and `host_denied`, a connection of another address, who is connected), `agent-permissions.test.ts` (the kinds, the parse, never taking the level from the model, the taint guard), `agent-groups.test.ts`, browser `genie-connections.spec.js` (Connect with a token that is not kept, the agent's cards in order, a tool that is not in the list, the request flow, no approval) and `admin-skills-plugins.spec.js`.

## 24a. Connections hardened, protocol upgrade and sign-in (2026-11-20)

From the review of the same day (`mcp-architecture-review-v2.md`). Built in `genie_conn_ticket.go`, `genie_conn_oauth.go`, `genie_mcp.go`, `genie_conn.go`.

**Approval is the server's.** What the page sends as `confirmed` counts for nothing. A write or a call that cannot be undone goes in three steps: `propose` (connection, tool, exact arguments, task, `tainted`) gives a ticket; `approve` (the person's answer on the card, `remember: "session"` for "Allow for this session") marks it; `call` with the ticket uses it up. A ticket is bound to the person, task, connection, tool, a hash of the arguments, and a hash of the tool's own description and schema (a service that changes a tool is asked about again); it ends after two minutes and works once, also when it is refused. A session grant is the server's too: one connection, writes only, four hours, never for what cannot be undone, never when `tainted` says the task holds text from outside, ended by Connect, Disconnect and a new sign-in. A server restart drops tickets and grants: the page then shows the card again (`needsCard`). Reads need no ticket.

**The route.** `genie_conn` answers only the page's own JSON request (`sameOrigin`: JSON content type, `Sec-Fetch-Site`, `Origin`). Arguments are checked against the tool's schema before anything is sent (required, types, unknown names only where the schema forbids them). A tool of a service from a link can only be made more careful by its annotations (a `readOnlyHint` lifts nothing); a service the site ships may say read. The token is sent only to the address it was given for (a changed address refuses the call), and a redirect to another host is refused.

**The protocol.** `mcpSession` / `dialMCP` is the one way a connection reaches a server. A server met for the first time is asked `server/discover` (2026-07-28); a server that answers it is spoken to without `initialize`, with `Mcp-Method` and `Mcp-Name` headers; one that does not (an error, or no JSON-RPC answer) gets `initialize` as before and `DELETE` when the session ends. What a server spoke is remembered (`mcpModes`). **Not tried against a real 2026-07-28 server**: its shape here is from the specification and the SDK's source.

**Signing in.** A catalogue entry may have an `oauthDef` (authorization code with PKCE and the client id and secret from `OPENREPL_<…>` variables, the admin's). GitHub: a GitHub App with user authorization (`OPENREPL_GITHUB_APP_CLIENT_ID`, `OPENREPL_GITHUB_APP_CLIENT_SECRET`, callback `<site>/genie_conn_oauth`, `OPENREPL_PUBLIC_URL` when the site is behind a proxy that hides its address). `oauth_start` makes the address (state and verifier kept on the server, ten minutes, once, only for that person); the callback swaps the code, tries the token with a real call, and seals the access and refresh tokens (`kind: "oauth"`). The access token is renewed 60 seconds before it ends, single-flight for a connection, and the new pair is written before the new access token is used (GitHub replaces the refresh token each time). A refused renewal marks the record `reconnect` (no retry; the list shows "Sign in again"); a renewal that cannot be reached keeps the old token while it lasts. A pasted token stays as the fallback. `RFC 9207` (`iss`) is checked when a provider sets an issuer. A second provider is a data entry (`oauthDef`).

**Not built:** finding a service's endpoints and registering the client by itself (protected-resource metadata, client registration), a task grant that covers calls after outside text (the server refuses a grant then; the page asks), several gateways (files and tickets live on one), the test against real GitHub (does its MCP endpoint accept a `ghu_` token, what each tool needs) and the cookie's SameSite value.

**Where the records live (2026-11-21, `genie_conn_store.go`).** The per-person records and the list of requests are no longer files in `/gottyTraces/genie-connections` (not in any backup, lost when a host keeps no disk between deploys). They are records of the user database `user_sessions.db`, the one of the profiles (MongoDB or Firestore when the site has one, else a file that the object-store backup covers): `genie-conn:<uid>` holds one document for each person (`{v:1, uid, updated, integrations:{<id>:{enabled, enabledAt, connection?:{kind, url, sealed, expires, account, connectedAt, renewedAt, reconnect}}}}`, the credential sealed as before with the person and the connection in its associated data), and `genie-conn-req:all` holds the requests (one list, at most 500). Both keys have a colon, which the list of users skips like `worker-pin:<uid>`. The old files are read once when the database has nothing for that person, imported and removed. A Disconnect removes only `connection`: the service stays enabled. The call log stays in daily files, is not persisted on purpose (admin sees the recent calls), and files older than 14 days are removed once a day. Tests: `TestTheRecordsAreInTheUserDatabase…`, `TestAnEnabledServiceWithoutAConnection…`, `TestTheOldFilesAreImportedOnceAndRemoved`, `TestTheCallLogIsKeptFourteenDays`.

Tests: `genie_conn_security_test.go` (cross-site and non-JSON refused; tickets once, per call, per person, past their time, a changed tool; grants and taint; levels; arguments; redirects; a 2026 and a classic server; sign-in with PKCE, state and issuer; 30 calls renew once and keep the new pair; refused and unreachable renewals), `e2e/tests/genie-connections.spec.js` (the stub keeps tickets).

## 25. Integrations: servers that an admin manages (2026-11-21)

Canvas: claude.ai/artifact/4SvDQfUd4FR6v8Xv9mi6AF (10 boards, all decisions approved). Files: `genie_integrations.go` (the data, the registry, the audience, secrets), `genie_integrations_admin.go` (routes, test, sign-in detection, tool policy, registration), `genie_integrations_requests.go` (a person's request, the admin's answer), `resources/js/admin-integrations.js` (the page), `plugins-dialog.ts`, `agent-groups.ts`.

**The registry (phase 1).** The servers are records in the settings document, `SiteSettings.Integrations` (the form of the Settings page never sends them and a reply never carries them; `/admin/integrations` changes them with the settings' own version, retried when the store moved on). The first call on a site with none writes GitHub from the list in Go (`connectionCatalogue`, now only the seed) as published, for everyone, its tools untested (the seed's levels stay in force). A record: id, name, description, keywords, address (https), status (`draft`, `tested`, `published`, `off`), the sign-in (`none`, `token`, `oauth`; `auto` for Genie's own registration), the audience (everyone, or e-mail addresses and accounts), limits (only lower than the site's 20 calls for a task and 60 a minute), the tools' policy, the last test. People see a published server in their audience (an admin also sees a draft or tested one, to sign in and test it). Switching a server off hides it at once and stops every call; a person's saved sign-in stays. Plugins that name `{"id":"github"}` find it in the registry.

**Test and tool policy (phase 2).** POST `admin/integrations` ops `save`, `test`, `tools`, `publish`, `unpublish`, `delete`, `secret`; every one writes a line to the admin audit log (never a value). A test (`testIntegration`) makes no call of a tool: it reads how the server signs people in (a 401 and its `WWW-Authenticate`, the protected-resource metadata of RFC 9728, the authorization server's metadata of RFC 8414: `registration_endpoint` and S256 make it `auto`), what it speaks (`server/discover` or `initialize`), and lists the tools with the credential the admin gave for it (a discovery token) or the admin's own sign-in to it; a server that wants a credential and has none is only looked at, and the page says so. A tool is `ToolPolicy`: off when first seen (new), off and marked changed when its description or schema changed since the admin looked, a level `read`, `write` or `restricted` (the gateway's `irreversible`: a card every time, never remembered, never after outside text); a tool cannot be on without a level. The gateway lists to Genie only the tools that are on, at the admin's level, whose live digest equals the saved one (a tool the server changed since is refused before any test); a server with no policy yet keeps the old behaviour. Secrets (the OAuth client secret, the discovery token) are sealed under `OPENREPL_SECRET` in `SiteSettings.IntegrationSecrets`, write-only, and never used on a person's call.

**The catalogue and the sign-in (phase 3).** `genie_conn` ops `enable` and `disable` (enabling an open server connects it at once; switching off keeps the credential), `list` rows carry `enabled`, `description`, `keywords`, `mode`. Sign-in: automatic OAuth (`registerClient`: dynamic registration, RFC 7591, once for each address of the site, a public client with PKCE, the `resource` of RFC 8707 on the authorization and token requests, the issuer check of RFC 9207 when the server says it sends it), or an OAuth app the admin made (client ID typed, secret sealed), or the person's own token (the admin's note says how to get one). A renewal uses the client of the address the sign-in came back to (`connRecord.Redirect`). An integration's own limits are counted per person and task. The page's word list for the connect group is now data: `connectWords` from the names and keywords of the list the server gave, so that a new server needs no change of code; and a task that is about a server the person has not switched on shows a card once ("Notion is available for you", Enable and sign in) and goes on without it.

**Ask for a server (phase 4).** `genie_conn` op `ask` (name, address, what Genie should do, what the person thinks the sign-in is, a docs link): text only, 10 waiting requests a person, one for the same address, refused when the server is already available to the person; kept in `genie-conn-req:all` (Kind `server`). The admin's answer (`admin/connection-requests`, `approve_user`, `approve`, `customize`, `decline`): the first two make the integration (or find the one with that address), set the audience (the person, or everyone), test it, switch on the tools the server calls read-only at the level read, and publish it when that is enough, else it stays a draft with the reason; `customize` makes a draft only. The person sees the status in Requests, and "Ready: enable it and sign in" when it is published for them.

**Not built:** an audience of groups, usage per server, an alert when a tool changes (the Integrations page shows it at the next test), a persistent log of writes, an OAuth app made by Genie for a server that offers no registration (the admin makes it), and nothing was tried against a real server with automatic OAuth (the tests use a fake one that offers all of it).

Tests: `genie_integrations_test.go` (the seed, add, test, policy, publish, enable, a changed tool, who sees it, limits, secrets, detection and registration, a request and the answers), `e2e/tests/admin-integrations.spec.js`, `genie-connections.spec.js` (Enable of an open server, Ask for a server), `agent-groups.test.ts`.
